# Architecture

Evolution is governed by the [canonical prompt contract](docs/contract/README.md).
Its [per-cut state and prerequisites](docs/contract/status.json) distinguish existing
closed profiles from planned composition, external dependency closure and independent
installation admission. Planning a family does not enable it in the runtime/product.

COMPOSE-01 now has a [private candidate inspection](docs/COMPOSITION_CANDIDATE.md)
after its [in-memory preview](docs/COMPOSITION_PREVIEW.md). It reuses the preserving
engine, emits distinct composition metadata, accounts for all file bytes and
reopens a temporary JAR for exact ZIP/resource/ASM/linkage checks. Its typed result
exposes only a report/hash, never candidate bytes or an installation approval.
The six ordinary conversion profiles and public runtime capability are unchanged.

The subsequent [developer QA export](docs/COMPOSITION_QA_EXPORT.md) lives in a
separate `compositionQa` source set, excluded from all player/CLI artifacts. It
borrows already proven bytes through a package-private scoped callback and writes
a hash-bound QA directory, not a product conversion/installation receipt. The
public inspection API still exposes no bytes. Native comparison remains pending.

The dev-only corpus tool now supplies a [read-only disposable run plan and
recorded exit checker](docs/COMPOSITION_RUN_PLANNING.md) for that exact candidate.
It verifies reviewed platform/launcher metadata and produces immutable directives;
it neither stages nor runs them. Post-exit checking consumes unsigned records and
does not observe a process or approve installation. The subsequent
[unarmed staging and internal process collector](docs/COMPOSITION_STAGING_COLLECTION.md)
provide create-new copied trees/journals and bounded child/pipe mechanics, tested
only with inert helper JVMs. The subsequent [closed inert session](docs/COMPOSITION_INERT_SESSIONS.md)
reconstructs a reviewed materialized stage, binds its receipt/inputs to an exact
test-helper command and publishes bounded unsigned post-exit evidence create-new.
Read-only recovery never replays a process. The native argv is not executed and
the test helper is not shipped. A [finite native output-layout policy](docs/COMPOSITION_NATIVE_OUTPUT_POLICY.md)
now separates immutable inputs, fixed properties and bounded opaque generated
files without approving their content. Native content/arming/execution/comparison
remain pending. The [exact static launcher audit](docs/COMPOSITION_NATIVE_LOOKUP_AUDIT.md)
does not rewrite platform archives or claim complete dynamic lookup closure.
None of these QA tools is reachable from or bundled in the player workflow.

The subsequent [finite native configuration review](docs/COMPOSITION_NATIVE_CONFIG_REVIEW.md)
checks exact generated defaults without invoking Forge or changing files. Its
separate necessary-file inventory distinguishes missing outputs from mere presence;
neither establishes a successful save, native execution or launch safety. Native
version checking, automatic loader threads and TARGET LAN advertisement remain
explicit concerns even when the inspected defaults are correct. World/log/trace
content and the original/target native comparison remain independent pending gates.

The [restricted settings proposal](docs/COMPOSITION_RESTRICTED_SETTINGS.md) now
binds a finite authored configuration set to a reverified unarmed stage and
refuses conflicts with every explicit baseline property. It returns immutable
text/hashes/recipes in memory only; it neither materializes a template nor
changes stage receipts, native argv or the previous default-review policy.
Restricted Forge settings are not OS network isolation: exact authlib startup
can fetch service keys independently. Native consumption/save, materialization,
process containment and original/target behavior remain unverified.

## Read-only equipment semantics

[Iron sword inspection](docs/IRON_SWORD_INSPECTION.md) is a typed operation on the
same bounded service, with an explicit selected hash and full local mapping/API
data. The developer CLI calls it directly. It validates the original structure,
ASM/linkage, API declarations and finite resources, then returns immutable
UNSUPPORTED evidence for unimplemented inherited mining and ToolAction contracts.
It has no output path, target serialization, adapter, install authority or public
profile. Constructor recognition and declaration correspondence cannot promote
semantic confidence. Pinned source facts are labelled separately from caller-
supplied declaration checks. The original is rehashed before returning evidence.

[Iron helmet inspection](docs/IRON_HELMET_INSPECTION.md) adds a separate finite
operation with the same service boundary and no publication path. It checks the
native IRON/HEAD construction and source linkage, then reports contextual
EquipmentSlot-to-ArmorItem.Type and occupied-slot use differences. Its diagnostic
does not map HEAD globally, create an empty runtime adapter or approve the target
native swap behavior. API indexes and pinned historical body facts remain
distinct evidence; the six conversion profiles remain unchanged. The subsequent
[fixed empty-slot runtime operation](docs/IRON_HELMET_EMPTY_SLOT_ADAPTER.md) adds
one versioned factory descriptor without enabling a constructor recipe or candidate.
The final native subclass is packaged but never registered by LegacyBridge startup.
Its compiled override and received-stack behavior are checked separately from the
still-unqualified inherited Equipable, dispenser and equipment-hook contracts.

The [guarded HEAD-effect operation](docs/IRON_HELMET_HEAD_EFFECTS.md) is additive
and does not change that item. Exact native player identities, HEAD and the fixed
stack shape are checked before the native sound call and armor-list write. A
separate physically guarded helper contains client class literals. This operation
is not composed with use or bound to a constructor recipe; copy ownership, thread,
external sound events and other inherited contracts remain explicit gates.

The [closed dispenser operation](docs/IRON_HELMET_DISPENSER.md) preserves native
query arguments, first-result selection and split/equip/drop/persistence for exact
ServerPlayer/Zombie. It reuses the guarded player effect, but writes Zombie HEAD
silently after a real-list preflight. Unknown first receivers reject before
consumption, never skip or return false. Native query enumeration differs between
versions and remains unqualified. This separate operation is not registered for
an item; no constructor recipe or candidate is enabled. A new explicitly owned
successor is required to compose these contracts without changing the old guards.

## Private owned attribute contract

[Owned item attributes](docs/ITEM_ATTRIBUTE_CONTRACT.md) now use an independent
two-class/six-method preserving candidate. Complete structural/frame bounds run
before source ASM dataflow allocation. Exact mappings and independent offline
linkage verify the native virtual override, protected inherited UUID identities
and the four reviewed Guava calls against explicitly selected source/target APIs.

The immutable main-hand pair is preserved; no game callback, player state or
NBT/event processing is emulated. A separate resource inventory does not erase
bodies. The candidate is serialized, reopened and independently rechecked; only
report/hash escape the bounded service. Two implemented OFFLINE metadata
generators provide distinct provenance, not public installation authority.
Unknown Guava/external references and combinations with other private contracts
remain blocked. Native equipment/combat/tooltip/multiplayer comparison is pending.

## Private attribute and durability composition

The [combined item contract](docs/ITEM_ATTRIBUTE_DURABILITY_CONTRACT.md) is a
distinct two-class/seven-method candidate with two native callbacks and exact
durability-128 factory order. It is not an automatic union of feature flags.
After checking all original bounds, effects and removed metadata, its structural
checker builds a deep admission-only view to reuse the attribute grammar.
That view never reaches transformation; all original executable bodies are kept.

The compiler, offline callback policy and reopened semantic proof each admit the
combination explicitly. Two new OFFLINE metadata generators identify this private
candidate without changing any previous adapter descriptor or runtime ABI.
The bounded service returns only proof/hash. Durability capacity, repair predicate
and attributes do not imply wear, anvil consumption, native qualification or Apply.

## Private guarded stack helper

The [owned stack contract](docs/OWNED_STACK_DAMAGE_CONTRACT.md) separately admits
two classes/five methods. It preserves a final Item constructor and a single
guarded damage-minus-one helper. Complete original bounds precede dataflow.
Exact compiler recipes and independent source/target/reopened linkage verify
native Stack finality, declaring/access contracts, superclass/interface sets and
unshadowed IForgeItem default hooks. A renamed helper may not collide with any
inherited declaration.

No class or method is replaced with a bootstrap. Candidate serialization has
explicit ownership and two implemented OFFLINE metadata operations; the bounded
typed service returns only proof/hash and deletes scratch on success or cancellation.
Public profiles and installation are unchanged. The endpoint adds no gameplay
caller, server/thread authority, inventory synchronization or native qualification.

## Private native item use

The [owned stack repair-use contract](docs/OWNED_STACK_REPAIR_USE_CONTRACT.md)
adds one separately proved native override to the guarded helper. A checked
admission-only copy reuses helper checks; all six original bodies, debug metadata
and resource bytes are preserved in the actual candidate. Native use dispatch,
the inherited hand getter, logical-side field and result factories require exact
mapping recipes and independent source/target/reopened linkage.

The bounded typed service exposes only proof/hash. Its distinct OFFLINE
manifest/binding operations neither enable a public profile nor grant installation.
Client SUCCESS prediction, server CONSUME/PASS and native creative damage
restoration remain explicit. Native behavior, thread/sync and multiplayer gates
are not inferred from bytecode validation.

## Private finite block contracts

The shared preserving engine now has independent plain, horizontal and
[static bottom-half geometry](docs/STATIC_SHAPE_BLOCK_CONTRACT.md) admission
operations. The latter preserves the owned Block subclass, constant shape field
and both native callbacks. Required native declarations are checked by both the
mapping compiler and the offline linkage verifier; an absent/private callback
cannot silently become an ordinary owned method.

The half-shape STONE recipe has a distinct OFFLINE adapter descriptor even though
its implemented native call sequence matches the plain-block recipe. Matching
instructions do not confer the full-cube recipe's semantic permission. The optional
existing self-drop table is checked as bounded data and byte-preserved, never
fabricated; native RNG/explosion-context differences remain explicit. Resources
and proofs are validated again after serialization. Typed operations return only
private proof/hash and discard scratch archives; public grammars, Apply and runtime
ABI are unchanged. Native qualification remains a separate gate.

The separate [boolean-toggle interaction contract](docs/BOOLEAN_TOGGLE_BLOCK_CONTRACT.md)
preserves the owned state initializer, native builder and guarded use callback.
A logical-client return precedes every world write; the only server write uses
the callback world/state/position and literal update flags. Source/target mappings
and reopened offline linkage independently require the native override owners and
access contracts. The two matching visual states are checked as an exact local
three-model graph. This reuses the full-cube STONE operation, not the half-shape
permission. Private manifest/bindings and the logged target mining tag do not
grant a public profile, installation approval or native gameplay qualification.

## Included player-profile data

The [bounded history API](docs/JOB_HISTORY_READ.md) reads schemas 1/2 on the
existing product coordinator, separate from live/actionable jobs and transaction
authority. It never creates a workspace, opens JARs or infers activation. Its
headless acceptance does not include a native history widget or reconciliation.

The player default uses [embedded simple-content contracts](docs/EMBEDDED_SIMPLE_CONTENT_DATA.md).
`MappingData.Kind.BUILTIN_SIMPLE_CONTENT` supplies a byte-pinned inert vocabulary,

incomplete and admitted only by the existing simple bootstrap interpreter.
CLI and native UI choose the same service input; explicit local data takes
precedence and errors never trigger fallback. Other profiles, generic mappings
and complete-bundle export reject this scope. No semantic rule or runtime ABI changes.

## Player product and implementation boundary (P1–P5)

The [job-install receipt correction](docs/JOB_INSTALL_RECEIPTS.md) appends schema-2
presentation receipts per affected job/installation attempt, independently from
the authoritative transaction journal. It adds no install authority, actionable
job rehydration, new conversion contract or runtime ABI. The read-only history
API is separate from those authorities. Native qualification remains
bound to each actual public artifact, not inherited from headless tests.

The accepted product is one mandatory public `LegacyBridge.jar` with an in-game
conversion menu. Its storage, phase separation, installation/restart limits and
current-versus-planned boundaries are defined in
[Product architecture](docs/PRODUCT_ARCHITECTURE.md), with the
[implementation sequence and acceptance gates](docs/PRODUCT_IMPLEMENTATION_PLAN.md)
and [pinned loader/UI API evidence](docs/PRODUCT_API_BASELINES.md).

P1 adds the JDK-only `legacy-workflow` executable contracts. P2 exposes the
shared asynchronous engine, extracts the neutral compatibility API and adds
explicit portable local mapping data. Neither milestone packages the combined
JAR, adds a button, installs mods or restarts Minecraft. P3 now adds
`legacy-product`: the combined artifact, a physical-client title button/screen
and the bounded controller's inventory -> analysis/conversion -> staging slice.
`legacybridge_runtime`, its exact adapter ABI and `simple-content-v1` remain
unchanged. P4 adds the native queue/details workflow; P5 adds separately approved,
journaled installation, explicit recovery and guarded manual closing. Automatic
launcher restart and hot activation are not implemented. See
[transaction contracts](docs/TRANSACTIONAL_INSTALLATION.md) and their separate
[validation ledger](docs/TRANSACTIONAL_INSTALLATION_VALIDATION.md).
[Packaging architecture](docs/PACKAGING_ARCHITECTURE.md) records
the selected exact-platform/JarJar strategy and separate production acceptance
gates; implementation alone does not satisfy those gates.

The implemented conversion path now uses the [ASM transformation pipeline](docs/ASM_PIPELINE.md).
Its readers/remappers preserve applicable debug metadata, its explicit adapter
recipe consumes only the proven finite registration graph, and offline
CheckClassAdapter/reference checks gate the actual output bytes before commit.
TransformationLog records each structural/body/resource change with exact rule,
confidence and adapter provenance. Analyzer and mapping-inspection paths remain
read-only; this does not enable arbitrary legacy API rewriting.

## Objective and boundary

The development-only `legacy-corpus` module depends on `legacy-converter`, never
the reverse. The product/runtime do not depend on or package it. Its bounded
catalog verifier checks exact artifact identity, authorization evidence and
independent validation chains. Its observation runner calls the existing typed
engine service with explicit local mappings; it does not duplicate rules,
execute originals, install outputs or inherit gameplay status. See the
[corpus schema](corpus/SCHEMA.md) and [prioritized backlog](corpus/BACKLOG.md).

Static engine work and target runtime support remain independent. The neutral
`legacy-compat-api` shares their existing ABI, while `legacy-workflow` separately
models the player-facing lifecycle without coupling the engine to Forge:

```text
untrusted Forge 1.16.5 JAR
            |
            v
  development CLI ---------+
                          v
  client Screen -> Controller -> LegacyEngineService (Java 17)
    analyze/mappings -> inspection reports (no conversion authority)
            |
            | plan: proves the grammar privately, no output
            | convert: repeats proof and publishes only a complete candidate
            v
  staged transformed JAR + explicit dependency on legacybridge_runtime

  LegacyBridge.jar (Minecraft 1.20.1 / Forge 47.4.23 / Java 17)
    legacy-runtime + shared engine/contracts + client-only interface
    explicit target-native adapters; no same-session activation
```

Both static inspection and the narrowly scoped `simple-content-v1` conversion
path are implemented. Conversion lowers a fully proven registration graph to
declarative content data and a Java 17 bootstrap calling the target-native
runtime adapter. It never modifies the input or executes source mod code.
This is not general binary remapping; see [Simple content](docs/SIMPLE_CONTENT.md).
The `0.1.1-SNAPSHOT` contract binds each transformation to an implemented,
versioned compatibility operation. Existing unbound converted JARs must be
reconverted; a previous fixture success does not validate the new artifacts.

## Module boundaries

### `legacy-converter`

The converter is a normal Java application and remains independent of Forge and
Minecraft at runtime. Its current code contains:

- typed asynchronous inventory, analysis, mappings, planning, conversion and
  explicit mapping-data preparation through `LegacyEngineService`;
- the `analyze` CLI with stdout-by-default JSON and stable exit codes;
- the `mappings` CLI with independent symbol inventory and a versioned mapping
  report derived from local official/MCP tables and ASM API declarations;
- the fail-closed `convert` CLI, finite ASM registration interpreter, strict
  resource validator, concrete adapter selection/bindings, target metadata/pack
  updates, generated STONE mining tags, and deterministic JAR emitter;
- a bounded, no-follow temporary input snapshot, ZIP/JAR validation, and
  SHA-256 fingerprinting of the exact bytes analyzed;
- inert manifest and Forge `mods.toml` parsing;
- ASM 9 classfile, exact reference counters, bounded per-class external
  reference details, and namespace analysis;
- path/content and inert Mixin, access-transformer, coremod, and manifest
  inventories;
- streaming Forge/Minecraft feature classification and deterministic risk
  scoring;
- an immutable `CompatibilityReport` graph and canonical JSON writer.

The commands are `analyze`, `mappings`, the separately gated `convert`, and
explicit setup/export through `prepare-mappings`. CLI handlers submit typed
service requests and wait off any game thread; they do not repeat engine rules.
Dedicated test-only configurations resolve exact Forge artifacts for selected
API baseline assertions, but those artifacts are not implementation or runtime
dependencies.
The converter no longer depends on a variant of the Forge runtime project.
It depends on neutral `legacy-compat-api`, containing only JDK-compatible
catalog/descriptor/selection contracts and offline adapters. No game classes
are introduced. SLF4J's API is a normal engine dependency; `slf4j-simple` is
added only to CLI distributions/launchers and tests, not the engine's normal
runtime dependency variant. The product assembly excludes the CLI package and
all its logging libraries, using Forge's existing provider instead.

The internal packages are:

```text
dev.legacybridge.converter
|- cli          command parsing, streams, and stable exit codes
|- service      typed asynchronous facade, bounded worker/queue, job outcomes
|- operation    cooperative deadlines, payload budgets and publication barrier
|- archive      bounded JAR access and normalized entry inventory
|- metadata     manifest and META-INF/mods.toml facts
|- config       inert Mixin, AT, coremod, and manifest configuration facts
|- content      resource-pack/data-pack path inventory
|- bytecode     classfile facts and symbolic references
|- namespace    definition/reference classification
|- analysis     feature, dependency, version, package, and risk classifiers
|- policy       progressive-support assessment
|- mapping      symbols, confidence, generated rules, resolution, mapping report
|  |- source    bounded local mapping loading, provenance, ASM API indexes
|  `- portable  explicitly selected inert mapping/API bundles and hashes
|- conversion   all-or-nothing content validation and target JAR emission
|  `- extract   bounded static registration interpreter and immutable content plan
`- report       immutable model and canonical JSON serialization
```

The analyzer list will be fixed by LegacyBridge code. Input JARs must never be
allowed to contribute analyzer plugins, service providers, or executable code.

### Reusable service API (P2)

The public facade is
`dev.legacybridge.converter.service.LegacyEngineService implements AutoCloseable`.
It has a default constructor and `LegacyEngineService(EngineOptions)`.
Applications should own one long-lived instance, not create a worker pool for
each click. No service operation calls the CLI, uses stdout as IPC, invokes
`System.exit`, registers content or loads a source mod class.

| Public method | Typed result | Effect |
|---|---|---|
| `inventory(Path directory)` | `EngineJob<InventoryResult>` | Bounded, non-recursive candidate enumeration and static summaries; never Forge discovery |
| `analyze(Path input)` | `EngineJob<CompatibilityReport>` | Existing analyzer schema 2 |
| `mappings(Path input, MappingData data)` | `EngineJob<MappingReport>` | Existing mappings schema 1; no conversion authority |
| `plan(ConversionRequest request)` | `EngineJob<ConversionPlan>` | Full finite proof and private candidate serialization, but no destination published |
| `convert(ConversionRequest request)` | `EngineJob<ConversionResult>` | Same proof followed by validated, no-replace publication; existing conversion schema 2 |
| `prepareMappings(MappingPreparationRequest request)` | `EngineJob<Path>` | Explicit local mapping/API export into a new directory |
| `close()` | `void` | Reject new work and request cancellation without blocking or interrupting a publication already begun |

`ConversionRequest` carries normalized input/output paths, `MappingData`, and
`Optional<String> expectedInputSha256`; the three-argument constructor omits
the optional fingerprint. Supply the selected lowercase SHA-256 to detect a
changed candidate between inventory and conversion. An output request does not
authorize overwriting, installing or activating a mod. The product controller
supplies an owned staging destination, not an arbitrary `mods` path.

`MappingData.builtinSimpleContent()`, `MappingData.bundle(Path)`,
`MappingData.profile(Path)` and `MappingData.unavailable()` make the data source
explicit. Only the finite simple-content profile accepts the included provider.
There is no implicit Gradle-cache fallback. Unavailable data produces `MAPPING_DATA_REQUIRED`.
`MappingPreparationRequest(Path output, Optional<Path> profile,
boolean fromDevelopmentCache)` requires exactly one selected source: an
explicit profile or explicit development-cache preparation. It downloads
nothing and does not populate a missing development environment.

`EngineJob<T>` exposes `id()`, `completion()`, `latestProgress()` and `cancel()`.
Completion is a `CompletionStage<EngineOutcome<T>>`, not a log stream.
`EngineOutcome<T>` contains `status`, `Optional<T> value` and
`Optional<EngineError> error`:

- `COMPLETED`: a result is available; analysis/mapping findings may still
  require review, and completion is never gameplay validation.
- `BLOCKED`: a refusal plan/conversion report and structured diagnostic are
  available, but no result JAR is published.
- `FAILED`: an operational error without a result.
- `CANCELLED`: cancellation took effect before publication, without a result.

`EngineError(code, message, remediation)` carries bounded, display-safe text.
Codes distinguish missing mapping data, rejected archives, I/O failure,
`QUEUE_FULL`, `SERVICE_CLOSED`, unsupported conversion, timeout and payload
limits. Invalid Java API arguments can reject synchronously when constructing
requests/submitting them; normal worker failures arrive through the outcome.

`InventoryResult(directory, entries, truncated)` retains summaries, not whole
bytecode reports. Entries include a path, optional fingerprint, mod declarations,
source profile, complexity/risk, duplicate-mod-ID flag and optional error.
Duplicate checks apply only to the bounded observed input set, not installed
mods or dependency closure. A truncated result must be displayed as incomplete.

`ConversionPlan` contains convertibility, source/prospective-output paths,
source hash, optional candidate hash and a separate `LEGACY_CONVERSION_PLAN`
schema-1 report. Its status is `PLANNED` or `ABORTED`; `output` remains null and
`transformationsCommitted` remains false. Planning uses the exact conversion
proof, then discards private candidate bytes. `convert` intentionally redoes
the proof and rehashes the source before committing. A saved plan or editable
report is never an installation capability or a reusable unchecked candidate.

Default execution is one daemon worker, eight queued requests and at most 128
inventory candidates. Requests in the queue retain paths/options, not loaded
JARs or indexes. Default per-job source, inflated-work and captured-payload
limits are 64 MiB, 128 MiB and 64 MiB, with a two-minute cooperative deadline
including queue time. `EngineOptions` permits bounded queue/inventory changes
and explicit `OperationLimits`. Fixed parser/archive/mapping bounds also apply.
These payload budgets are not a hard heap or wall-clock isolation guarantee.

`latestProgress()` exposes the latest `OperationProgress(stage, completed,
total, detail)`. `total=-1` means unknown, not zero percent. Stages correspond
to real inventory, scan, mapping, semantic/ASM/resource validation, preparation
and publication work. The native UI polls bounded controller snapshots on its
client tick; it never `join`s a job on the render thread. Other consumers must
likewise poll bounded state or marshal completion onto their own UI thread.
Non-async completion continuations can run on the completing worker or on the
caller cancelling a queued job; keep them short and dispatch explicitly.
The service cannot prevent an application's own callback from blocking its
caller. Retaining completed jobs/reports indefinitely is also the caller's
responsibility.

Cancellation is cooperative. `cancel()==true` prevents starting publication;
queued cancellation also frees the queue slot. After the final publication
barrier or completion, `cancel()` returns false. Closing requests cancellation
but does not wait for cleanup; process shutdown must not falsely imply all
workers have already stopped. Owned temporaries are closed/cleaned on ordinary
failure or cancellation; abrupt process loss is not transactional crash recovery.
See [execution controls](docs/ENGINE_EXECUTION_CONTROLS.md) for opaque parser/OS
latency and filesystem-race boundaries.

### `legacy-compat-api`

This neutral Java 17 module owns the eight unchanged compatibility catalog,
descriptor, selection, writer, exception and offline-adapter source files.
The existing `dev.legacybridge.runtime.compat` packages, runtime version and
adapter IDs/signatures are preserved. The module has no compile/runtime
dependencies and no Forge metadata, services, nested JARs or foreign classes;
its verification task audits that boundary and required classes.

The runtime uses its main source output on compile/test/validation paths,
in Forge development mod sources and in generated catalog execution. The final
runtime JAR and sources include the same definitions exactly once. The old
runtime `compatApi` source set, `compatApiElements` variant and `compatApiJar`
task are removed. Neither this JAR nor `legacy-workflow` is installed as a mod.

### `legacy-runtime`

The runtime is a Forge mod compiled against exactly Minecraft `1.20.1` and
Forge `47.4.23`, using official target mappings. Its entry point is the real
Forge annotation `net.minecraftforge.fml.common.Mod`, and its logger comes from
the target environment through `com.mojang.logging.LogUtils`.

`RuntimeDescriptor.current()` truthfully declares:

- Minecraft `1.20.1`;
- Forge major `47`;
- runtime bytecode transformations disabled;
- the single aggregate `simple-content-v1` declarative-content capability.

This state comes from an immutable typed `RuntimeCapabilityCatalog` and is also
published as `META-INF/legacybridge/runtime-capabilities.json`. Defining the
capability types alone is not evidence of support. A separate implementation
catalog at `META-INF/legacybridge/adapters.json` documents 69 operations, including
the original eleven simple-content operations and separate developer contracts.
Catalog availability does not enable a conversion profile. The enabled capability accepts
only the strict plan and exact adapter bindings, not arbitrary legacy APIs.

The runtime must never define replacement classes in `net.minecraft`,
`net.minecraftforge`, `cpw.mods`, or another platform-owned namespace. All
adapters belong under `dev.legacybridge.runtime` and bytecode may reference
them only through a reviewed, exact transformation recipe.

Generated mod JARs require `legacybridge_runtime` and invoke the cataloged
`compat.registry.SimpleContentAdapter.register` entrypoint. Their mod-scoped
`adapters.json` binds IDs, revisions, classes, methods and descriptors to exact
runtime version `0.1.1-SNAPSHOT`. The runtime compares that data to its compiled
catalog before registration; it never reflectively loads supplied class names.
The old facade delegates to the same verification, not a compatibility bypass.

The eight compatibility areas are registry, event, world, client, entity,
networking, capability and rendering. The final four contain only explicit
unsupported documentation, no dummy adapters. Detailed operation contracts and
artifact boundaries are in [Compatibility layer](docs/COMPAT_LAYER.md).
Current artifact-bound build and game evidence is maintained separately in
[ASM-pipeline validation](docs/ASM_PIPELINE_VALIDATION.md). Architectural contract
validation is recorded separately in [P1 validation](docs/PRODUCT_ARCHITECTURE_VALIDATION.md).

### `legacy-workflow`

This internal Java 17 library contains immutable, side-effect-free workflow and
restart decisions plus read-only validation of instance-owned storage paths.
It has no runtime library dependency, Forge entrypoint, adapter, bootstrap
service, worker or installer. Root `build` checks its tests and packaging
boundary. `ConversionController` now uses `BridgeWorkspace` to validate and
revalidate the fixed instance directories. Installation lives in the product,
separate from conversion; no restart provider is enabled. See the product architecture
for its trusted-caller and filesystem-race limitations.

### `legacy-product`

This ForgeGradle assembly owns `ClientMenuHooks`, `ConversionScreen` and the
JDK-only `ConversionController`. Its final file is
`legacy-product/build/libs/LegacyBridge.jar`. It combines own runtime, neutral
API, engine and workflow outputs without embedding their internal JARs or
duplicating conversion rules. The only JavaFML entrypoint remains
`LegacyBridgeRuntime`, with mod ID `legacybridge_runtime` and exact adapter
catalog/runtime version `0.1.1-SNAPSHOT`. Do not install the old standalone
runtime alongside it.

The public metadata requires exactly Minecraft 1.20.1 / Forge 47.4.23. That
ordinary installation provides the engine's pinned ASM 9.9.1, NightConfig 3.6.4
and host logging; none is copied into the product. One unchanged SRG Utils 0.6.2
binary is included through Forge Jar-in-Jar with range `[0.6.2,0.6.3)`. JarJar
negotiates a shared library version across mods, not a private classloader.
Incompatible declared ranges fail loading. No relocation, arbitrary dependency
merge, copied game implementation or startup service is introduced. The
[packaging audit](docs/PACKAGING_ARCHITECTURE.md) documents the actual loader
source, module/package ownership and redistribution obligations.

Client discovery is restricted to `Dist.CLIENT` using Forge's event subscriber
boundary; common entrypoints/controllers do not resolve screen classes on a
dedicated server. The title hook is `ScreenEvent.Init.Post` on the main Forge
event bus, not a transformation or custom locator. The screen supports bounded
inventory, search and a serial 32-job conversion queue. TransactionScreen offers
approved batches of up to four, explicit inspection/resume/restore, managed
unloaded upgrades and safe apply-and-close. There is no automatic restart or
hot activation. Labels are localized in English and Portuguese; engine diagnostic
details retain their structured technical messages.

Each screen owns one controller. The controller accepts at most one active
action and uses a one-worker/one-queued-task coordinator; one engine worker
performs the static work. Filesystem operations, report serialization and waits
run off the client/render thread. UI ticks poll immutable bounded snapshots.
Closing requests cancellation without waiting; cancellation cannot be accepted
after publication has begun. A later report-write failure must keep a committed
staged artifact visible, not mislabel it as cancelled or absent.
Installation is non-cancellable and shares the coordinator, preventing overlap
with conversion. A singleton JDK shutdown hook retains accepted installation
leases through ordinary JVM shutdown; it neither executes originals nor calls
the game thread. Forced termination still requires journal recovery.

Workspace directories are created only by the explicit controller workflow,
after path validation. Originals remain in `legacybridge/input`. New output
and report destinations use operation-owned subdirectories beneath staging and
reports, with no overwrite of the original, an existing result or `mods`.
The default simple-content conversion uses the included finite contracts when
the mapping field is blank. Explicit full-data selection uses an absolute local
bundle directory; the suggested `legacybridge/cache/mapping-data` is not
automatically searched or downloaded. Unknown contracts remain fail-closed.

The artifact includes project-owned schemas, catalogs, profile rules and the
byte-pinned finite simple-content declaration contract, not a complete locally
generated mapping/API database. Expanded-data redistribution and SRG Utils
corresponding-source/license compatibility remain release review gates.
A single mandatory JAR does not solve broad mapping availability, general
profile installation, restart or universal conversion.

## Static-analysis pipeline

`AnalysisService` coordinates this pipeline:

1. Validate that the input is a readable regular file and within fixed limits.
2. Read a bounded EOCD/ZIP64 preflight, rejecting excessive entry counts,
   central-directory size, multi-disk input, and invalid directory bounds
   before `ZipFile` builds its index.
3. Fingerprint the original bytes with SHA-256, then open the archive without
   extraction or class loading.
4. Build a deterministic, normalized entry inventory while enforcing
   per-entry, aggregate-byte, aggregate-name, and compression-ratio limits.
5. Parse canonical `META-INF/MANIFEST.MF` and `META-INF/mods.toml` as data.
6. Read classfiles with ASM and collect versions, definitions, descriptors,
   annotations, instructions, handles, constant dynamics, and module/nest/
   record metadata.
7. Emit every ASM reference occurrence synchronously to exact feature/platform
   counters, then fold the class into the archive aggregate. A failed class
   scan does not commit partially observed references.
8. Retain at most 256 distinct reference samples per class/archive view and at
   most 256 per-class detail records, with exact occurrence counters and
   explicit truncation flags. Sampling attempts for ordinary references and
   each top-level platform family stop after 4,096 observations; hierarchy
   edges bypass that attempt budget and have retention priority. Definition
   indexing remains complete for readable classes under the archive's
   50,000-entry ceiling.
9. Inventory assets/data paths and parse bounded loader configuration as inert
   text/JSON. A non-conventional Mixin path declared by the manifest triggers
   one bounded second archive pass and an input-fingerprint comparison. A
   missing declared config, malformed/truncated config, or more than 256
   distinct manifest `MixinConfigs` declarations makes analysis `PARTIAL`.
10. Classify facts and risk markers without claiming semantic compatibility.
11. Apply the current allowlist policy.
12. Verify that the source fingerprint did not change, serialize one canonical
    report, and leave the input unchanged.

No stage uses `ClassLoader`, `URLClassLoader`, `Class.forName`, reflection on
input classes, `ServiceLoader`, Forge discovery, ModLauncher, or a Minecraft
process. ASM analysis visits existing frames and does not use `ClassWriter` or
frame computation that resolves classes. Custom opaque JVM attributes are not
interpreted and cannot support a compatibility conclusion.

Security requirements for this pipeline are in [docs/SECURITY.md](docs/SECURITY.md).

## Mapping inspection pipeline

`MappingAnalysisService` reads the same bounded JAR input through a separate
ASM reference pass with a 20,000-symbol ceiling. It does not derive its input
from truncated analyzer report samples. Owners, methods, fields, constructors,
and valid descriptor observations enter an exact-symbol inventory; class
evidence and oversized components have independent explicit limits.

Generic mapping inspection and developer profiles use an explicit local profile
or hash-verified portable bundle; the included incomplete provider is only for
simple-content conversion. `MappingInputsLoader` remains the lower-level
development loader: it reads pinned Mojang ProGuard/MCP TSRG files from an
explicit properties profile, or from the development cache only through
explicit preparation/legacy development API calls. It hashes all input
sources and checks pinned default mapping hashes. `ApiIndex` inventories
declarations in official-mapped Forge API JARs without class loading. Local
API hashes establish provenance, not publisher authentication. No stage
downloads dependencies or allows a mod to supply mapping plugins.

`PortableMappingBundle` stores declaration-only metadata, not Minecraft/Forge
classfiles or implementations. Its schema-1 manifest records exact baselines,
namespaces, original source hashes and each payload's length/SHA-256. Consumer
loading does not need original development-cache paths. This is a local-use
export, not an approved distributable mapping pack; see
[portable mapping data](docs/PORTABLE_MAPPING_DATA.md).

`MappingDatabaseGenerator` composes source SRG and development aliases into
official identities, requires exact official target symbols, and corroborates
declarations/staticness/visibility against source and target inventories.
Target production symbols combine Mojang class names with SRG member names;
raw target TSRG `C_*` owners are not production owners. Missing/ambiguous
symbols yield review states. The five semantic refusal anchors and contract
changes lacking an implemented direct-call adapter are `UNSUPPORTED`; a
whole-plan content adapter cannot satisfy arbitrary legacy calls.
Package candidates are heuristic evidence only.

`MappingDatabase` resolves immutable rules by full key and composes descriptors
all-or-nothing. Generated structural matches have `HIGH` confidence;
`VERIFIED` requires separate semantic validation. No generated mapping can
authorize rewriting. `MappingReport` records the four resolution statuses,
seven change categories, provenance, per-symbol evidence, and incompleteness
separately from `CompatibilityReport` v2. See [docs/MAPPINGS.md](docs/MAPPINGS.md)
for profiles, exact namespaces, and the real baseline example.

## Metadata is evidence, not proof

Both supported lines use `META-INF/mods.toml`, and regular JavaFML mods use the
real `net.minecraftforge.fml.common.Mod` annotation. That common shape does not
make their APIs binary-compatible.

Likewise, `loaderVersion="[36,)"` is not sufficient to prove that a file was
built specifically for Forge 1.16.5; the open upper bound also contains later
major versions. A future source-profile assessment must correlate independent
facts such as the Minecraft dependency range, Java classfile distribution,
entrypoint annotations, platform references, and legacy-only markers. Even
then, the result is a candidate classification rather than execution proof.

The source-profile classifier parses only a conservative numeric subset of
Maven ranges, requires valid unique mod IDs and an explicitly mandatory
Minecraft dependency owned by a declared mod, and otherwise leaves the profile
ambiguous. Its loader range must intersect Forge major 36; a separate Forge
dependency cannot substitute for that source-profile requirement. The
top-level `detectedForgeVersion`, independently, may use either the JavaFML
loader range or a declared Forge dependency as weak evidence for `36.x`.
Qualifiers, unions, variables, and other unsupported but structurally valid
range syntax produce a warning and are excluded from numeric inference rather
than making the TOML unparseable. This is another reason the profile remains
advisory.

Selected metadata facts are recorded without general interpolation; long text
values and the modeled field set are deliberately bounded. The one modeled
Forge convention, `${file.jarVersion}`, resolves only from the allowlisted
manifest `Implementation-Version`, otherwise it becomes `UNKNOWN`. The
converter does not contact `updateJSONURL`, follow manifest `Class-Path`, or
resolve declared dependencies during analysis.

Metadata uncertainty is itself modeled as `METADATA_UNCERTAINTY` when
`mods.toml` is missing/unparsed, no valid mod ID exists, or `loaderVersion` is
blank. A parsed non-`javafml` loader is the separate `UNSUPPORTED_LOADER`
feature. Manifest `Class-Path` is recorded as `EXTERNAL_CLASS_PATH`. Legacy
`TweakClass` or `ForceLoadAsMod: true` hooks are recorded as
`LEGACY_BOOTSTRAP`; none of these declarations is followed or invoked, and the
bootstrap hooks have no Forge 47 execution path.

## Bytecode facts

Java 8 classfiles normally use major version 52. Java 17 accepts older valid
classfiles and uses major version 61, so major 52 alone is not an incompatibility
and must never be mechanically rewritten to 61. The fixed classfile header is
validated and retained before ASM traverses the body, so a trustworthy major
version above 61 is still blocked when the remaining bytes are unreadable. Any
unreadable class prevents the 1.16.5-candidate profile. A preview class, an
unsupported multi-release layout, or malformed bytecode is a blocker or review
finding according to the policy.

Definitions and references are separate facts. For example:

- referencing `java/lang/String` is normal;
- defining a class under `java/` is prohibited;
- referencing `net/minecraft/`, `com/mojang/`, or `net/minecraftforge/`
  identifies a platform dependency, not whether that dependency still exists
  in the target;
- defining copied platform classes under Minecraft, Forge, or ModLauncher
  namespaces requires rejection or explicit review;
- string constants resembling class names are heuristic evidence only.

Collection is bounded before canonical ordering: types enter one of eight
fixed categories, occurrence counters remain exact, and only the first 128
distinct internal names per category and direction are retained. The report
emits 12 of those names and explicit truncation state. Archive special-entry
evidence is similarly retained per risk kind, so one noisy kind cannot evict
all evidence for another.

An actual compatibility conclusion requires an exact owner, member name,
descriptor, invocation kind, and mapping context checked against the pinned API
baselines. Namespace prefix replacement is never an acceptable transformation.

## Report architecture

The implemented schema-v2 report starts with the requested analyzer fields:

```text
schemaVersion
modId / modVersion
detectedMinecraftVersion / detectedForgeVersion
classCount
minecraftReferences / forgeReferences
thirdPartyDependencies
mixins / accessTransformers / coremods
unsupportedFeatures
riskScore / complexity
packagesUsed / classReferences / content / manifest
tool
input
archive
metadata
bytecode
markers
findings
assessment
```

The detailed class section groups external samples into `superclass`,
`interfaces`, `methods`, `fields`, and other referenced `types`. Each member
reference preserves its input JVM-form owner, member name, descriptor, and
reference kind unless an adversarially long component hits the documented
report-retention cap; that case sets a truncation flag. This is intentionally
not a mapping or target-side resolution.

Risk weights are applied once per detected feature family, not once per API
occurrence. Required declared third-party mods and class-count scope add bounded
amounts. Access transformers, nested JARs, signed JARs, multi-release JARs,
external manifest classpaths, and uncertain metadata impose at least
`MODERATE`; Mixins and unsupported loaders impose at least `COMPLEX`; coremods,
transformation services, native code, and legacy bootstrap hooks impose at
least `EXTREME`. Thresholds are `0..14` SIMPLE, `15..34` MODERATE, `35..59`
COMPLEX, and `60..100` EXTREME. Policy finding severity remains a separate
axis: for example, a transformation blocker can still have a `MODERATE`
migration-effort classification. The score estimates review effort only.

Nested records expose the analysis, source profile, conversion, and execution
states separately. Lists and maps are defensively copied and sorted, findings
have stable codes/severity/evidence, and the writer uses fixed property order,
UTF-8, LF, and a final newline. See
[docs/REPORT_SCHEMA.md](docs/REPORT_SCHEMA.md) for the exact contract.

The current assessment separates:

- whether analysis completed;
- what source profile the evidence suggests;
- whether runtime testing was performed.

The general analyzer's historical v2 conversion state remains unconditionally
`NOT_IMPLEMENTED`: that report does not run or authorize the subset converter.
The separate schema-v2 `LEGACY_CONVERSION` report records the support profile,
source provenance, `CONVERTED`/`ABORTED` outcome, compatibility status, structured
transformations with concrete adapter references, exact `adapterBindings`,
preserved resource hashes and output fingerprint. Mapping inspection remains
schema 1; the analyzer remains schema 2. No report establishes runtime-test success.

## Transformation boundary

The sole implemented lowering is the finite declarative registration/resource
grammar documented in [Simple content](docs/SIMPLE_CONTENT.md). It is a semantic
adapter path, not a promotion of generated `HIGH` mappings to rewrite permission.
The current profile accepts only basic COMMON/non-damageable/non-fire-resistant
items, STONE blocks with STONE sound, and absent/MISC/BUILDING_BLOCKS categories.
Source vanilla tag declarations are refused. A named offline adapter creates
the target pickaxe-mining tag needed to retain legacy STONE tool behavior;
accepted source resources remain byte-identical. This is a necessary addition,
not an exception allowing arbitrary data migration.
Any additional transformation recipe must have:

- a stable capability ID and version;
- an implemented catalog entry documenting source API, target API,
  transformation, behavior differences, limitations and motivating fixtures;
- exact source symbols confirmed in the pinned 1.16.5/36.2.42 baseline;
- exact target symbols or runtime adapter confirmed against 1.20.1/47.4.23;
- positive and negative synthetic fixtures;
- deterministic transformation output;
- post-write bytecode and package verification;
- target-side tests proportionate to the affected API.

Unknown or only partially covered requirements block JAR production. The
default path must not emit partially transformed artifacts.

## Build architecture

All five root modules use a Java 17 toolchain. Runtime and product apply
ForgeGradle and depend on the exact target Forge artifact. Archive tasks use reproducible ordering
and omit source timestamps. Gradle parallelism is disabled because the shared
workspace and ForgeGradle caches are not treated as independent build targets.
The neutral JDK-only compatibility API JAR is a converter dependency, not a
player mod. The public product packages concrete runtime adapters and the same
shared contract exactly once. Its catalog is generated from the implemented descriptors,
not maintained as an unrelated hand-written list.

The development CLI distribution remains separately runnable and retains its
own dependency set. A separate QA probe artifact can exercise the packaged
product on a normal Forge installation, but is never included in the public
JAR and is not a player dependency. Root artifact audits reject fixtures,
harnesses, private mapping payloads, services, duplicate classes and unexpected
nested binaries. Third-party library sources/notices included for compliance
are not Minecraft sources or execution dependencies.

A successful Gradle build proves compilation, unit tests, resource processing,
and packaging only. It does not prove mod discovery, client safety, dedicated
server safety, conversion correctness, or legacy-mod execution.
